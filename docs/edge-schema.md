# 邊的 schema

> 這份文件定義卡片裡 `--` 的資料形狀。**它還沒有變成程式碼** —— `src/lib/bread/types.ts` 現在
> 還沒有邊這種東西，那是 #15 的工作，而 #15 要等模型形狀定了才動（「先知道要放什麼，再決定盒子
> 長怎樣」）。這裡先把「要放什麼」寫清楚。
>
> 前置：#14（`--` 的三種型別，已結案）。後續：#22（代價需要幣別）、#19（星座）、#24（抽成純資料）。

## 為什麼需要這個

現在卡片裡的邊是純文字。人看得懂，機器看不懂，而且三種不同的東西長得一模一樣：

```
#豐富度/零 -- 沒有油膜，麵筋不被 shorten -- #麵筋/高      ← 因果
#豐富度/高 -- 油 shorten 麵筋 -- #麵筋 的「達成成本」↑     ← 代價
-- pasta madre：每天餵、養好幾年                          ← 前提（而且沒有起點）
```

#14 已經把它們數出來並命名了。這份文件補上剩下的欄位。

## 形狀

```ts
type Edge = {
  from: EndpointRef[]   // 一或多個來源（多個 = 卡片裡的 `+`）
  to: EndpointRef       // 一個終點
  kind: "因果" | "代價" | "前提"
  strength: "hard" | "soft"
  reason: string        // 卡片 `--` 中間那段字，原封不動搬過來
  note?: string          // 卡片括號裡的補充（出處、旁白、警語）
}
```

前案是 Marble 的 [os-taxonomy](https://github.com/withmarbleapp/os-taxonomy)，他們每條邊是
`{ topicId, prerequisiteId, strength: "hard"|"soft", reason }`。我們比他們多兩件事：`kind`（他們
只有 prerequisite 一種邊）、`from` 是陣列（他們不支援超邊）。

### 為什麼 `from` 是陣列，`to` 不是

卡片裡的 `+` 是**超邊（hyperedge）**：

```
#豐富度/零 + #糖/無 -- 沒有上色來源 -- 靠高溫 + 蒸氣 + 長發酵的殘糖
```

「豐富度零」跟「糖無」不是兩條各自成立的邊，是**兩個條件湊在一起才有這個結果**——拆成兩條會失真。
RDF 跟 property graph（Neo4j）原生都只支援點對點，標準解法是把邊本身變成節點（reification）。
我們的資料量還很小，直接讓 `from` 收陣列就夠了，不用先付 reification 的複雜度。

`to` 維持單一，是因為卡片裡目前沒有出現「一條邊指向兩個終點」的例子。真的出現時再拆——**現在讓它
單純，比預先通用重要。**

## `strength`：hard 還是 soft

判準只有一句：**這條邊被推翻的話，是「這張卡錯了」還是「換個看法而已」。**

| | 意思 | 例子 |
|---|---|---|
| `hard` | 物理／法律的必然。做得到反例就是這張卡寫錯了 | 油 shorten 麵筋 —— 沒有例外 |
| `soft` | 傾向、類比、通常如此。有反例不代表邊是錯的 | 含水量高 → 大氣孔（整形爛掉一樣沒氣孔） |

3D 星系需要這個欄位才知道線要畫多粗、鏡頭拉遠時哪些邊該先淡掉。**#19 的星座如果每條線一樣亮，
看起來就是一團毛球。**

⚠️ `hard` / `soft` 講的是**這條邊有多必然**，不是**做起來有多難**。難度是 #22 的 `cost`，掛在
「代價」型別的邊上，兩者互不相干：布里歐「油 shorten 麵筋」是 hard 邊（必然發生）但代價可以用時間
付掉；「含水量高 → 大氣孔」是 soft 邊卻不用付任何代價。

## `reason`：一句話，用卡片的語氣

Marble 把 reason 設成必填，理由值得抄：**沒有理由的邊，之後審查的人無從判斷對錯。** 我們的資料是
自己手寫＋查證的，更需要——半年後回來看一條邊，reason 欄是唯一能分辨「這是我查過的」還是「這是我
當時猜的」的東西。

語氣照卡片來，不要寫成規格書：

```
✅ 都是低油高水，差別只在你有沒有耐心整形
❌ 兩者於含水量與油脂含量維度上具高度相似性
```

（reason 是「為什麼有這條邊」。「這句話哪來的」是 `source` / `confidence`，屬於 #24，不要塞進
reason 裡。）

## 端點可以是四種東西，不是只有軸

這是實際編碼三張卡時撞出來的，原本沒想到：

```ts
type EndpointRef =
  | { kind: "axis";      axis: AxisKey; level?: string }  // #豐富度/高
  | { kind: "bread";     id: string }                      // BV-003
  | { kind: "outcome";   text: string }                    // 「不規則大氣孔」「空洞」
  | { kind: "technique"; text: string }                    // 「pasta madre」「兩段麵團」
```

沒有這四種的話，卡片裡有一半的邊放不進來：

- 法棍「沒有油鎖水 -- 老化快，24 小時就不行」的終點是**結果**，不是軸。
  （這也是 #17「沒有任何一條軸是結果」的另一面：結果不是軸，但結果是端點。）
- 潘娜朵尼那五條「懸空的邊」——`-- pasta madre：每天餵…`——#14 說它們沒有起點。編碼之後發現
  **它們不是沒有起點，是起點不是軸**：起點是「不想投降的潘娜朵尼」這顆麵包本身，終點是技術。
  懸空只是因為當時的符號沒有麵包這種端點可用。
- #19 的星座（法棍 ↔ 巧巴達）兩端都是麵包。

## 三張卡編碼後的樣子

把現有的 `--` 全部走一遍，一共 14 條。這是這份 schema 的驗證：**每一條都放得進去，沒有需要新欄位的。**

### 法棍 BV-001

| from | to | kind | strength | reason |
|---|---|---|---|---|
| #豐富度/零 | #麵筋/高 | 因果 | hard | 沒有油膜，麵筋不被 shorten |
| #豐富度/零 | 老化快，24 小時就不行 | 因果 | hard | 沒有油鎖水 |
| #含水量/中高 | 不規則大氣孔 | 因果 | **soft** | 麵團夠鬆，氣孔撐得開 |
| #豐富度/零 **+** #糖/無 | 高溫＋蒸氣＋長發酵殘糖 | 因果 | hard | 沒有上色來源，色是「省」出來的 |

### 布里歐 BV-002

| from | to | kind | strength | reason |
|---|---|---|---|---|
| #豐富度/高 | #發酵/低 | 因果 | hard | 油包澱粉 → 澱粉酶構不到 → 分解不出糖 → 酵母沒飯吃 |
| #豐富度/高 | #麵筋（成本↑） | **代價** | hard | 油 shorten 麵筋，值照樣到 95，只是要揉更久 |
| #豐富度/高 **+** #糖 **+** #蛋 | 爐溫必須反向調低 | 因果 | hard | 上色快到不像話，金色是「多」出來的 |
| 麵筋出來 | 加油 | **前提** | hard | 油先進去就先包住麵粉，麵筋永遠出不來 |

最後一條原本在 L5「手」，不在 L4「勾稽」。它其實是一條標準的前提邊，只是因為講的是**順序**才被寫在
手感區。卡片自己的旁白已經說了：「一模一樣的參數，不同順序，做出不同的麵包。」

### 潘娜朵尼 BV-003

| from | to | kind | strength | reason |
|---|---|---|---|---|
| #豐富度/極高 **+** #發酵/極高 | 空洞 | 因果 | hard | 油包澱粉斷糖源，糖又用滲透壓抽乾酵母 |
| BV-003 | pasta madre | 前提 | hard | 每天餵、養好幾年甚至跨代，開工前還要 3 次預備續種 |
| BV-003 | 耐糖酵母 | 前提 | hard | 長期餵糖篩選出來的菌株（或 SAF Gold） |
| BV-003 | 特高筋麵粉 | 前提 | hard | 扛得住大量奶油又撐得起長發酵 |
| BV-003 | 兩段麵團 primo/secondo | 前提 | hard | 分批給糖，讓酵母先繁殖夠 |
| BV-003 | 溫度與 pH 全程控制 | 前提 | hard | 錯一步就是磚頭 |

潘娜朵尼那五條前提**全部是 hard**，這不是我偷懶——那正是這顆星的性格。卡片自己的結論是「物理給的
模糊空間≈0」，編碼之後這句話變成一個可以被程式看見的事實：**它的入邊全硬。** 法棍相反，它唯一的
soft 邊落在整形上，所以「翻車了還是麵包」。

這正是 #22 想要的東西的雛形——難度是**算**出來的，不是我拍腦袋給的星等。

## 編碼過程發現的三件事

1. **`+` 只出現在因果邊上，沒有出現在代價或前提邊上。** 樣本只有三張卡，不足以下結論，但如果再
   多幾張卡仍然如此，`from` 陣列或許只有因果邊需要。先記著，不要現在就縮。
2. **代價邊只有一條**（布里歐那條）。#22 要拆的「幣別」目前只有一個實例撐著，所以 #22 動手前值得
   先多寫幾張卡——不然是拿一個樣本設計一套幣別系統。
3. **卡片沒有任何一條跨卡片的邊。** #19 星座要畫的線，資料上**還完全不存在**，一條都沒有。這比
   「schema 不夠用」嚴重得多：#19 缺的不是欄位，是內容。

## 還沒決定的

- **邊要不要有 id。** 沒有 id 就不能對邊留評論、不能被別的邊引用。等真的需要再加。
- **反向邊怎麼處理。** 「油↑ → 發酵↓」寫成一條有方向的邊，那「發酵低所以推得出油高嗎」？
  目前的答案是不行——邊是單向的，這符合實際（低發酵有很多種原因）。
- **`kind` 只有三種夠不夠。** 三張卡是夠的。第四種出現時再加，照 #14 的規矩：**先數再命名。**
