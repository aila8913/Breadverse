# Breadverse 的模式語言分析

> 用 Christopher Alexander《The Timeless Way of Building》的模式語言框架,對 Breadverse
> 做需求層次的架構分析。由 fable-advisor 於 2026-07-17 產出,記錄專案「感性優先」哲學
> 背後的設計裁決(design decisions),供未來的自己與協作者理解「為什麼這樣做」。

## 框架本身(30 秒版)

Alexander 的核心主張:好設計不是一條條「需求」,而是一組**模式(pattern)**——每個模式描述
「在某個脈絡下,一組互相衝突的力量(forces)反覆出現,某個解法能讓這些力量達成平衡」。GoF
把它正式化成 Context / Forces / Problem / Solution / Resulting Context 五欄。兩個關鍵一般
requirement doc 都做不到:

1. **Forces 必須誠實地互相打架。**「又快又好又便宜」不是 forces;「快會犧牲準」才是。解法的
   價值在它*怎麼裁決*這場架。
2. **模式必須連成語言。**單一模式沒有生命,模式 A 的 Resulting Context 要能自然引出模式 B。

---

## Pattern 1:3D 星系作為產品靈魂(不是裝飾)

- **Context** — 個人用食譜工具。市面上「更實用」的形式(表格、清單、2D 圖)早就存在。app 的
  名字「麵包星系地圖」本身就是承諾。
- **Forces** — 實用性拉力(3D 散點在資訊效率上*客觀輸給* 2D:遮擋、透視變形、讀值難)vs
  情感拉力(要的是漫遊、被驚豔)vs 工程成本(Three.js 額外技術棧 + 真實技術債:讀不了 CSS
  `var(--...)`,暗色模式壞掉 #11)。歷史證據:曾有人提議換成更實用的東西被否決——這場架真的打過。
- **Problem** — 若每次「體驗 vs 工程」都讓工程贏,產品會漸進退化成普通表格 app,名字承諾落空,
  使用者失去動力(學習型專案,動力就是生命線)。
- **Solution** — 把 3D 地圖明文寫進 `CLAUDE.md` 定為「靈魂與 WOW 點」,規定互動手感是核心投資
  不是 polish。它是 pattern 而非裝飾,因為它裁決了一整類未來衝突:任何「用 X 取代 3D 會更實用」
  預設答案是否。code 上它也真坐在版面最頂(`page.tsx:130`,在表單之前)。
- **Resulting Context** — 接受「瀏覽效率不是這畫面的目標」後,兩個新問題冒出:(a) 讀值需求由誰
  滿足 → 引出 **Pattern 7 表格雙生**;(b) 星星怎麼被篩選而不破壞宇宙感 → 引出 **Pattern 2**。
  留下已知債 #11。

## Pattern 2:夜空隱喻——濾鏡讓星星變暗,而不是消失

- **Context** — 第一位 TA 是使用者自己:低 richness 是硬底線、長發酵加分。需要「個人目標」過濾,
  發生在 Pattern 1 的星系宇宙裡。
- **Forces** — 任務效率(hide 讓人最快找到能吃的)vs 世界觀完整性(布里歐 richness 90 永遠過不了
  健康濾鏡,hide 等於宣告它「在你的宇宙裡不存在」)vs 價值中立(`never judges a bread`,hide 是
  一種評判)vs 視覺誠實(dim 保留全貌,代價是畫面更擁擠、對比更弱)。
- **Problem** — 標準實作(hide)會把「個人偏好」升格成「世界的邊界」,違反核心信念;但完全不過濾
  又讓健康目標無處安放。
- **Solution** — 濾鏡重定義為**鏡片(lens)**:不合條件的星變暗變小但保留座標。UI 語言換成
  亮星/暗星/星座。個人目標做成 preset,預設「顯示全部」。
- **Resulting Context** — 建立更深的公理「**app 沒有 fail state**」,直接生成 **Pattern 6**。
  誠實提醒:這個模式目前**只存在文件層**,`Bread3DMap.tsx` 裡還沒有 dim/shrink 或 preset
  程式碼(#7),是「已定案但未建成」。

## Pattern 3:混合建模——三軸推導、兩軸直錄

- **Context** — 五風味軸要從「食材克數 + 製作方法」算出,畫在雷達與 3D 上。
- **Forces** — 推導的純粹性(全從克數算最優雅,工程師本能想把五軸都變純函數)vs 物理現實(發酵
  時間與麵筋發展**根本不在重量裡**,硬反推是造假)vs 輸入負擔(直錄欄位每多一個表單就重一分)
  vs 一致性幻覺(五軸看似同質都 0-100,語意上一半是測量一半是自述,這裂縫日後會漏水)。
- **Solution** — `axes.ts:16-18` 的註解就是宣言:hydration/richness/grainStructure 從克數算;
  fermentationTime/glutenDevelopment 由 `RecipeMethod` 直錄。`CLAUDE.md` 注明「刻意決策,不是
  疏漏」,防止未來的自己或 AI「好心修掉」。
- **Resulting Context** — 可推導三軸引出 **Pattern 4**;直錄兩軸暴露新張力(分數表刻度是拍腦袋
  #16、`RecipeMethod` 容不下設備與水合法 #18)。更根本:#15 主張五軸其實是一張**圖(graph)的
  投影**,不是模型本身——這是模式語言正在自我修訂的活證據。

## Pattern 4:真實含水率——waterRatio 分解,而非天真烘焙百分比

- **Context** — Pattern 3 決定 hydration 從克數推導。烘焙界標準語言是 baker's percentage
  (水重/麵粉重)。
- **Forces** — 慣例簡單(只算「水」一行除法,對得上食譜書)vs 跨食譜可比性(星圖存在前提是同一
  座標系;布里歐標稱低水但蛋奶油藏大量水,天真算法把 lean/rich 麵團放進不可比的兩套尺度)vs
  資料維護成本(每食材要標 waterRatio,老麵還要拆 flourRatioInStarter,食材庫從名字清單變成要
  查證的科學資料)vs 與慣例偏離(算出來跟書上不同,要解釋「有效含水率」)。
- **Problem** — 座標系不統一星圖就是謊言,兩顆星相對位置無意義;但統一要付資料成本與認知成本。
- **Solution** — `computeTrueHydration`(`percentage.ts:52-66`)每食材乘 waterRatio 加總;
  starter 特殊處理;同一招復用在 richness(蛋只計固形物)與麵粉基準。**同一分解原則貫穿三個
  計算**——好模式的特徵:一次裁決,處處適用。
- **Resulting Context** — 座標系可信後,`classicBreads.ts` 手估參考點反成系統裡**最不可信的
  資料**(檔案自己承認)。引出「參考點也要從真實食譜推導」,目前半成品(`docs/cards/` 種子集)。

## Pattern 5:localStorage-only——刻意的無後端

- **Context** — 大二獨立學習專案、單使用者、無營運資源。社群分享明文定為 someday/lowest。
- **Forces** — 完整感誘惑(學習專案不做後端好像沒學到)vs 維護現實(部署/auth/遷移/資安全一人扛,
  唯一使用者就是作者)vs 資料風險(localStorage 會被清、不跨裝置、無備份,真實代價非零)vs
  未來遷移(UI 若直呼 `window.localStorage`,日後加後端等於重寫)。
- **Solution** — `storage.ts` 是薄隔離層:UI 只認 `loadRecipes/upsertRecipe/deleteRecipe`,
  註解明說「換後端只改這層內部」。**簡單但可逆**的教科書示範:用模組邊界買未來選擇權,而非用
  後端買現在的負擔。SSR 相容(`typeof window` + useEffect 掛載讀取)是這選擇在 Next.js 下的
  必要配套。
- **Resulting Context** — 無後端 → 無帳號 → 無多人 → 濾鏡天然是「單人視角鏡片」。留下張力:
  `JSON.parse` 無 schema 驗證、`Recipe.version` 恆為 "v1.0"(#12);當格式演化(#15 幾乎保證)
  沒有遷移機制的 localStorage 會第一個痛。

## Pattern 6:嚴謹的模型、放鬆的語氣——拉桿只註解、不評分

- **Context** — 使用者自述「想要嚴謹但也不想要嚴謹」。建模 session 找到真實矛盾:同一根拉桿上
  風味與健康可指相反(奶油在 10% 油脂下體積+風味俱勝 / JAMA 統計上奶油最高攝取組死亡率 +15%)。
- **Forces** — 知識的嚴謹(要準,錯的數字比沒有更糟)vs 規訓的拒斥(一旦畫上綠色「正確區」,
  app 就變教練/裁判,使用者從探索者變受評者)vs 矛盾不可調和(風味最優與健康最優在科學上就是
  不同點,任何單一評分都必須隱瞞一邊)。
- **Problem** — 怎麼讓模型既誠實承載嚴謹知識,又不把知識變規訓?多數產品在此二選一:要嘛評分
  (規訓),要嘛不給資訊(媚俗)。
- **Solution** — 拉桿**註解不評分**:告訴你「這油量下酵母會怎樣」,不告訴你「你做錯了」。沒有
  綠區紅區,app 沒有 fail state。這是 Pattern 2「dim not hide」在資訊層的同構複製——空間上不
  放逐任何麵包,語意上不判決任何選擇。
- **Resulting Context** — 「註解」需要有知識可註,引出 L4 勾稽層需求(#14/#15 的邊類型化)。
  目前這模式在 code 裡**完全還沒落地**(表單只是普通輸入框),是語言裡最新、最抽象但已有明確
  設計規則的一頁。

## Pattern 7:圖表的表格雙生(advisor 補命名)

每個感性圖形都配一個表格雙生——雷達圖旁軸值表(`page.tsx:295-315`)、3D 地圖下座標表
(`Bread3DMap.tsx:173-193`)。感性優先不能變成「犧牲可及性與精確讀值」的藉口;酷的部分負責
感動,表格負責誠實。呼應 Pattern 6。

## Pattern 8:框架無關的領域核心(advisor 補命名)

`src/lib/bread/` 零 React/Next import,UI 單向依賴它。`RadarInput = Pick<Recipe, "lines"|"method">`
更進一步:計算函式只索取真正需要的欄位,於是「存檔前即時預覽」不用捏假 id。**整個語言裡工程
品質最高的一頁**——模型可用 `tsx` 腳本驗證、未來可加 vitest(#10)、#15 的重構可在不碰 UI 下
進行。

## 模式語言完整性評估

**已成形且互相扣連的核心**(語言活的部分):

- **Pattern 1 → 2 → 6** 是清晰的價值鏈:「星系是靈魂」→「濾鏡不放逐星星」→「app 沒有 fail
  state / 只註解不評分」。三者共享同一深層公理(宇宙不評判),PROGRESS 明文記錄它們被*認出是
  同一信念*的時刻——這正是「連成語言」的樣子:不是六條獨立規則,是一個信念的六次顯影。
- **Pattern 3 → 4 → 8** 是技術側連貫鏈:混合建模 → 分解式計算 → 框架無關核心,程式碼全部落地,
  註解主動解釋 why。

**半成品**(有設計、無實作,對應 current gaps):Pattern 2 的 dim/preset(僅文件 #7、#1–#4);
Pattern 6 的註解拉桿(僅設計規則);Pattern 4 下游(`classicBreads.ts` 仍手估、`docs/cards/`
未接進系統);Pattern 5 隱憂(無 schema 驗證、無版本遷移 #12);3D 暗色主題 #11。

**語言正在自我改寫的一頁(最重要洞察)**:PROGRESS 的五層模型與 #15(「五軸是一張圖的投影,不是
模型本身」)不是又一個 gap,而是**一個更深的模式正在浮現,它會重寫 Pattern 3**。Alexander 會說
這是健康的——當卡片註記 `//#上色 #快` 塞不進五軸,語言自己長出新文法。專案處理它的方式完全是
Alexander 式的:「先數 `--` 有幾種再命名」(#14)、「先知道要放什麼再決定盒子」(#15 擋住
`types.ts`),讓 forces 自己說話。

**總評**:這專案的模式語言在**價值層已連成一體**(罕見地,一個學習專案有明文的、被實踐檢驗過的
產品哲學),在**實作層約完成一半**。最大風險不是哪個 gap,而是 **#15 的模型重構若處理不慎,可能
撕裂「嚴謹模型」鏈(3/4/8)與「感性宇宙」鏈(1/2/6)之間目前靠五軸維繫的接縫**——五軸正是兩鏈
交會點(圖是模型,軸是給星圖的投影)。好消息:Pattern 8 的隔離層意味這場手術可在 `src/lib/bread/`
內完成而不驚動宇宙。依 issue 依賴鏈(#14 → #15 → 其餘)動刀是對的順序。
